## ユーザーストーリーの優先順位付け

> ストーリーは [practice/userstory-practice.md](./practice/userstory-practice.md) の US-01〜US-19。
> 時間は `workload.md` の見積もり（1ポイント＝1時間）を使う。

### 優先順位の決め方

次の順番で並べる。

1. **MoSCoW**：Must → Should → Could の順（要件定義書の優先度）
2. **依存関係**：前提になるストーリーを先にする（例：投稿がないと一覧・編集が作れない）
3. **価値 ÷ 時間**：同じ条件なら、少ない時間で大きな価値が出るものを先にする

### 価値の基準（ヒアリングで聞いた困りごと）

| 価値 | 基準 |
|---|---|
| 5 | アプリの土台／3つの困りごと（業務の偏りが見えない・期限切れに気づかない・相談が流れる）を直接解決する |
| 4 | 困りごとの解決を助ける（詳しく見る・絞り込む・最新にする） |
| 3 | あると便利（探しやすい・伝わりやすい） |
| 2 | なくても業務は回る |

## スプリントの流れ（1週間）

```
Day 1  : スプリントプランニング（1時間）→ 開発作業
  ↓
Day 2-5: 開発作業
  ├── デイリースクラム（毎日15分）
  └── 進捗確認（バーンダウン：残りポイントを記録）
  ↓
Day 6  : バッファ（遅れ・バグ修正）
  ↓
Day 6  : スプリントレビュー（30分：動くものを確認）
  ↓
Day 6  : スプリントレトロスペクティブ（30分：KPT で振り返り）
  ↓
（次のスプリントへ）
```

### 各イベントでやること

| イベント | 時間 | やること |
|---|---|---|
| スプリントプランニング | 1時間 | スプリントゴールを決める／バックログから今週やる項目を選ぶ／タスクに分けて GitHub Issue にする |
| デイリースクラム | 15分 × 4日 | ①昨日やったこと ②今日やること ③困っていること（詰まりは30分以上抱えず質問する） |
| スプリントレビュー | 30分 | 完了の定義を満たした機能だけをデモする／ゴールの達成度を確認／残った項目をバックログに戻す |
| スプリントレトロスペクティブ | 30分 | KPT（Keep・Problem・Try）を書く／Try を1〜2個に絞り次のスプリントで実行する |

### 完了の定義（Definition of Done）

- [ ] 画面で動作を確認した（正常系・エラー系）
- [ ] バリデーションのエラーが表示される
- [ ] 他チーム・他人のデータが見えない／操作できない（権限が関係する機能）
- [ ] feature ブランチで作業し、`main` にマージした
- [ ] Issue をクローズした

## 遅れたときの対応

| 状況 | 対応 |
|---|---|
| そのスプリントのバッファで吸収できる | バッファを使い、計画は変えない |
| ゴールを達成できなかった | 残った項目を次のスプリントの先頭に入れ、プランニングで Should を削る（ブックマーク一覧 → 絞り込み → コメントの順） |
| Sprint 3 でも間に合わない | デプロイを後回しにし、ローカルで動く状態を完成とする（講師に相談） |
| 時間が余った | Could（F-17 ステータスの Ajax 更新 → F-18 コメント削除 → F-19 S3・CloudFront） |
