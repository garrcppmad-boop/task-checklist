# 技術選定：チーム業務共有ボード

> 要件定義書（[requirements.md](../requirements.md)）の制約条件・非機能要件をもとに、使う技術とデプロイ先を決めた理由をまとめたもの。

## 1. 使用技術一覧

| 分類 | 技術 | 選んだ理由 |
|---|---|---|
| 言語・フレームワーク | PHP / Laravel | 総合プロジェクトの指定。Policy・バリデーション・Eloquent など、必須の機能を標準で作れる |
| 認証 | Laravel Breeze（Blade 版） | 会員登録・ログイン・パスワードリセットの画面と処理が最初からそろう。登録画面にチームの選択を足すだけで済む |
| 画面 | Blade テンプレート | Breeze（Blade 版）と同じ書き方で統一できる。`{{ }}` で出力が自動でエスケープされ、XSS を防げる |
| CSS | Tailwind CSS | Breeze に最初から入っている。クラスを付けるだけでレスポンシブ対応ができる |
| Ajax | JavaScript の `fetch` | ブラウザ標準の機能なので、ライブラリを追加しなくてよい。ブックマークの切り替えだけなら十分 |
| データベース | MySQL | 総合プロジェクトの指定。授業で使ってきたので、つまずいたときに調べやすい |
| 画像の保存 | ローカル（`storage/app/public`） | 要件で S3 は発展課題としたため。公開環境では Render の Persistent Disk に保存する |
| セッション・キャッシュ | Render Key Value（Redis 互換） | Render はデプロイのたびにサーバーのファイルが消えるため、ファイルに保存するとログインが切れてしまう |
| 開発環境 | Docker（Laravel Sail） | PHP・MySQL のバージョンを公開環境と揃えられる。PC に直接インストールしなくてよい |
| テスト | PHPUnit（Laravel の Feature テスト） | Laravel に最初から入っている。ログイン・CRUD・権限（403）をテストする |
| バージョン管理 | Git / GitHub | 機能ごとにブランチを切り、Issues と Projects でタスクを管理する |
| デプロイ先 | Render（B） | 下の「2. デプロイ先の選定」を参照 |

## 2. デプロイ先の選定

### 候補

| 候補 | 概要 |
|---|---|
| A：AWS（EC2） | 仮想サーバーを借りて、Web サーバー・PHP・MySQL を自分でインストールして動かす |
| **B：Render（採用）** | GitHub と連携し、push するだけでビルド・公開まで行う PaaS（サーバーの管理を任せられるサービス） |

### 比較

| 観点 | A：AWS（EC2） | B：Render |
|---|---|---|
| 公開までの手間 | Web サーバー（nginx）・PHP・MySQL のインストールと設定が必要 | GitHub のリポジトリを選び、ビルドの設定をするだけ |
| HTTPS 化 | 証明書（Let's Encrypt など）を自分で取得・更新する | 証明書を自動で発行・更新する |
| デプロイ | サーバーに入って `git pull` などを手で行う（自動化には別の仕組みが必要） | `main` への push で自動デプロイ |
| サーバーの管理 | OS・ミドルウェアの更新を自分で行う | Render に任せられる |
| MySQL | 同じサーバーに入れるか、RDS を使う | マネージド DB が PostgreSQL のため、MySQL は Private Service として自分で立てる |
| 料金 | 無料枠（12か月）がある。超えると従量課金 | ディスク・Key Value を使うため有料プランが必要（月額固定） |
| 学べること | Linux・ネットワーク・サーバー構築の知識が身につく | アプリ開発に時間を使える。インフラの知識はあまり増えない |

### 選定理由（B：Render を選んだ）

1. **デプロイに使える時間が少ない**：スケジュールでデプロイに使えるのは8時間。EC2 ではサーバー構築と HTTPS 化だけで使い切るおそれがある
2. **HTTPS が自動**：非機能要件の「通信は HTTPS 化する」を、設定なしで満たせる
3. **稼働率 99% の目標**：OS の更新や障害の対応を Render に任せられるので、1人でも目標を保ちやすい
4. **GitHub の流れと合う**：機能ブランチ → PR → `main` にマージ、で自動デプロイされるので、毎週の進捗をすぐ公開環境で確認してもらえる

### Render にした場合の注意点

| 注意点 | 対応 |
|---|---|
| MySQL のマネージド DB がない | Private Service（MySQL の Docker イメージ＋ディスク）として立てる。外部には公開しない |
| デプロイのたびにサーバーのファイルが消える | 画像は Persistent Disk、セッションは Render Key Value に保存する |
| ディスクを付けたサービスは台数を増やせない | 利用者30名程度なら1台で足りる。増えたら画像を S3 に移す（F-19） |
| 有料プランが必要 | 構築前に料金ページで月額を確認する |
