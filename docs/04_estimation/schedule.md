# スケジュール：チーム業務共有ボード

> 工数見積もり（`workload.md`）をもとにした、開発3週間のスケジュール。

## 前提

| 項目 | 内容 |
|---|---|
| 納期 | 3週間（要件定義書「6. 制約条件」） |
| 作業時間 | 1日 7時間 × 週6日 ＝ **週 42時間**（3週間で 126時間） |
| 見積もり | 開発 98時間 ＋ バッファ 25時間 ＝ **123時間**（余裕 3時間） |
| 進め方 | Must → Should の順に作る。Could は時間が余ったときだけ |
| バッファ | 各週の最後にまとめて確保し、その週の遅れ・バグ修正にあてる |

## 全体の流れ

| 週 | テーマ | 開発 | バッファ | 合計 |
|---|---|---|---|---|
| 1週目 | 土台づくり（環境・DB・認証・業務の作成と一覧） | 33時間 | 8時間 | 41時間 |
| 2週目 | Must の機能を完成（CRUD・権限・画像・色分け・検索・ブックマーク） | 32時間 | 8時間 | 40時間 |
| 3週目 | Should と仕上げ（絞り込み・コメント・テスト・公開） | 33時間 | 9時間 | 42時間 |
| **合計** | | **98時間** | **25時間** | **123時間** |

## マイルストーン

| 時点 | 状態 | 確認すること |
|---|---|---|
| 1週目の終わり | ログイン〜業務の投稿・一覧ができる | 3チームの Seeder データでログインし、投稿が一覧に出る |
| 2週目の終わり | Must の機能が動く | 他人の業務を編集すると 403、期限の色分け、ブックマークの Ajax |
| 3週目の終わり | 完成・公開 | テストがすべて成功、公開 URL を HTTPS で開ける |

## 遅れたときの対応

| 状況 | 対応 |
|---|---|
| その週のバッファで吸収できる遅れ | バッファを使い、スケジュールは変えない |
| バッファを使い切っても遅れている | Should を後ろに回す（優先度の低い順：ブックマーク一覧 → 絞り込み → コメント） |
| 3週目でも間に合わない | デプロイを後回しにし、ローカルで動く状態を完成とする（講師に相談） |
| 時間が余った | Could（F-17 ステータスの Ajax 更新 → F-18 コメント削除 → F-19 S3・CloudFront）に取りかかる |
